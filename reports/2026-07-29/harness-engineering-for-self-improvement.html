用 Harness 工程构建可自我改进的 AI 系统

Harness Engineering for Self-Improvement
LilLog · Sat, 04 Jul 2026 00:00:00 +0000 · 影响分 10
打开原文 ↗

这不是原文摘要，而是把文章先翻译成中文语义后，再拆成可复用的思考方式、方法论和行动线索。

1. 核心观点

Harness 不是简单的提示词或传统的“模型＋记忆＋工具＋规划＋行动”，而是连接基础模型与真实环境的运行时系统。它决定模型如何思考和规划、怎样调用工具、如何执行动作、看到什么上下文、把哪些状态持久化，以及用什么标准验证结果。 作者给出了三类基础设计模式：

  • 工作流自动化：让 Agent 在“规划→执行→观察或测试→改进→再次执行”的目标导向循环中运行，并能根据失败轨迹继续迭代，必要时主动向用户澄清目标或执行偏好。
  • 文件系统作为持久记忆：不要把完整工作流、日志和产物全部塞进上下文，而要把实验日志、代码差异、论文摘要、错误轨迹和历史执行过程保存为文件，让 Agent 按需读取。
  • 子 Agent 与后台任务：由主 Agent 并行探索多个假设、运行实验或委派隔离任务，同时通过可检查的状态、日志和文件管理启动、监控、取消与结果合并。Harness 的优化对象还会逐级上移：指令提示词→结构化上下文→工作流→harness 代码→优化器代码。

最终目标不是继续堆砌人工规则，而是优化“获得更好答案的机器”，形成能够改进上下文、skill、工作流乃至 harness 本身的元方法。

2. 关键论据

第一，基础模型的评测智能不等于真实任务中的系统智能。Claude Code、Codex 等编码 Agent 的成功说明，同一个模型能否稳定完成真实工作，高度依赖外层系统如何组织工具、上下文、执行循环和结果验证。

  • 第二，长周期任务无法靠不断追加对话维持。实验日志、代码差异、错误栈和历史轨迹可能远超上下文窗口；如果全部注入提示词，上下文会快速失控。文件系统能将丰富状态持久化，同时让模型通过 grep、cat 等简单接口按需检索，避免把存储和注意力混为一体。
  • 第三，并行只有在“显式且可检查”时才真正有价值。子 Agent 的输出若只存在于临时聊天中，就会变得不可恢复、不可追踪；保存为文件、日志和状态记录后，主 Agent 才能在中断后恢复，并基于执行历史继续推理。
  • 第四，ACE 把上下文视为持续演进的行动手册，而非越来越长的提示词：Generator 产生轨迹，Reflector 从成功和失败中提炼经验，Curator 以带标识符的条目增量更新。结构化合并可以减轻反复整段重写造成的上下文坍塌和“越改越短”偏差。
  • 第五，MCE 把优化分成两层：基础层在给定 skill 下优化上下文；元层依据训练与验证指标，对历史 skill 进行组合和演化。它不再预设唯一的上下文结构，而是让 skill 与其条件化的上下文共同迭代。
  • 第六，Meta-Harness 进一步把“管理什么信息、怎样检索、怎样呈现”的代码本身变成搜索空间。强编码 Agent 可以像人类工程师一样创建、执行、评分和筛选 harness 候选，最终保留合格方案或帕累托前沿上的候选。

3. 方法论

第一层是任务循环。先定义可验证目标，再让模型反复执行“规划→行动→观察或测试→反思→改进”。关键不在一次回答，而在于 Agent 能否分析自己的轨迹和失败，并通过运行时继续行动。第二层是状态外置。把长期记忆拆成文件和目录：静态部分可包括提示词、知识库、代码库和 skill.md；动态部分可包括上下文条目、执行轨迹、实验数据、错误日志、评分与状态更新。

模型只把当前步骤所需内容加载进上下文。第三层是并行执行。主 Agent 负责拆分独立假设，子 Agent 或后台任务负责并发探索。主 Agent 需要具备最小进程管理能力：启动任务、检查状态与日志、取消失败任务、读取持久化产物、比较结果并合并回主线程。第四层是上下文学习。

ACE 使用 Generator、Reflector、Curator：先参考已有行动手册完成任务，再从成功和失败中提炼新经验，最后以“标识符＋描述”的增量条目更新手册；定期精炼和去重，而不是每轮重写整段提示词。第五层是 skill 与上下文联合演化。

MCE 将 skill 定义为静态组件与动态操作器的组合：静态组件承载提示词、知识和代码，动态操作器负责搜索、选择、过滤和格式化。基础层根据 rollout 反馈优化上下文函数；元层根据历史 skill、上下文函数及训练/验证指标组合出新 skill，以验证集表现防止只适配历史任务。第六层是 harness 搜索。

将候选 harness 封装为独立目录，保存源码、分数、轨迹和状态；由编码 Agent 提出新候选，实际执行并评分，只保留达标方案。此时被优化的已经不是答案或提示词，而是生成和改进答案的运行机制。

4. 金句摘录

“A harness is the system surrounding a base model that orchestrates execution and decides how the model thinks and plans, calls tools and acts, perceives and manages context, stores artifacts, and evaluates results.”——Harness 是包围基础模型的系统，负责协调执行，并决定模型如何思考与规划、调用工具与行动、感知与管理上下文、保存产物以及评估结果。

这一定义明确了 Agent 工程的主体不是提示词，而是完整运行时。“Improving the machinery for getting better answers, not just improving the answer itself.”——改进的是获得更好答案的机器，而不只是改进答案本身。这是作者所说“元方法”的核心。

“The progression in the object being optimized in the harness system is roughly: instruction prompts → structured context → workflow → harness code → optimizer code.”——Harness 的优化对象大致沿着“指令提示词→结构化上下文→工作流→harness 代码→优化器代码”逐步上移。

“Context as an evolving playbook rather than an increasingly lengthening prompt.”——应把上下文看成持续演进的行动手册，而不是不断变长的提示词。重点是经验条目的增量维护，而非聊天记录的无限累积。

“Once harness design becomes an executable search space, a strong coding agent can exploit the same design space human engineers use.”——一旦 harness 设计成为可执行的搜索空间，强大的编码 Agent 就能利用人类工程师使用的同一设计空间。

这意味着 AI Coding 不只用于写业务代码，也可以用于改造 Agent 自身的工作机制。

5. 我的行动

1. deepweek 个人助手：把长期目标、本周一事、每日事项、排序理由、完成记录和复盘分别保存为结构化文件，不依赖单次对话记忆。建立“读取长期目标→生成候选事项→按目标贡献和生活底盘排序→用户确认→每日执行→周末复盘→更新规则”的 loop。每条排序规则使用稳定标识符，记录它来自哪次成功或失败，避免反复重写整个提示词。

  • AI Signal Radar：把抓取、最近三个月过滤、去重、影响力评分、正式入库和丢弃原因拆成可执行工作流。Reddit、Product Hunt、GitHub 和其他来源可作为并行子 Agent，各自把原始结果、过滤结果、证据和错误日志写入独立目录；主 Agent 只读取摘要和候选条目，完成跨源去重、证据审计与最终合并。
  • 930 前工作流全部 Agent 化：不要用“是否接入大模型”作为完成标准，而要检查每个流程是否具备五项能力：目标定义、执行 loop、持久状态、工具权限、结果评估。先挑高频且可验证的流程改造，再从失败轨迹中沉淀上下文条目。只有在多个任务上验证有效的规则，才升级为通用 skill。
  • 个人 IP 创建：把选题发现、资料收集、观点提炼、初稿生成、事实核验、渠道改写、发布和数据复盘做成工作流。小红书、公众号和抖音脚本可由并行子 Agent 处理，但共用一份“个人判断与案例库”。每次发布后的阅读、收藏、咨询和转化作为验证指标，驱动选题与表达 skill 演化，而不是仅凭主观感觉改提示词。
  • AI Coding 实践：将每个 Agent 的 harness 放进独立目录并版本化，至少包含 skill.md、context、rollouts、artifacts、evals 和 state。让编码 Agent 在测试环境中提出 harness 修改、运行回归任务、比较新旧指标；未通过验证的修改不得进入正式工作流。

每项正式入库结论都要能追溯到来源和评分依据，借鉴原文提到的可验证性与证据链约束。

6. 第一性原理

模型只有在看到正确状态、能采取真实行动并获得可判定反馈时，才可能通过循环改进。因此，单纯提升提示词或无限扩大上下文，并不能自动产生长期可靠性。

  • 第一，存储不等于上下文。系统可以保存全部历史，但模型当前只应看到与决策相关的压缩信息；文件系统负责持久化，检索和上下文工程负责选择，二者必须分离。
  • 第二，没有评估就没有自我改进。Agent 如果无法判断执行结果是否更好，只能产生更多轨迹，不能形成有效学习。评估必须进入运行时，而不是任务结束后的附加说明。
  • 第三，失败必须可观察。错误日志、轨迹、代码差异和状态变化若没有持久化，Agent 就无法比较方案，也不能从中提炼可复用经验。
  • 第四，并行的本质是扩大假设搜索，而不是增加角色数量。只有可独立执行、可检查、可取消、可比较并可合并的子任务，才值得交给多个 Agent。
  • 第五，真正的递归改进需要改变生成结果的机制。提示词优化仍在改答案；工作流、skill、harness 和优化器的演化，才是在逐步改造“如何获得答案”。
  • 第六，harness 应保持简单、通用和可组合。复杂逻辑应被封装，接口应尽可能稳定，这既类似操作系统，也能利用模型在预训练中学到的软件工程知识，避免智能模型被脆弱的启发式规则束缚。

7. 真需求

对长期运行的 Agent，用户真正需要的是任务中断后能够恢复，而不是每次重新解释背景；需要结论能追溯到日志、证据和产物，而不是相信一次生成；需要失败任务可取消、问题可定位，而不是让多个 Agent 在聊天窗口中制造更多文本；需要系统从历史执行中形成可复用经验，同时避免上下文无限膨胀。

对 AI 工程团队，真需求是把 Agent 从“提示词资产”升级为“可测试的软件系统”：有明确输入输出、工具协议、权限边界、持久状态、后台任务、运行日志、评估集和回归机制。对 skill 建设，真需求不是积累越来越长的说明，而是分清三类内容：长期稳定的静态知识、可执行的动态操作器、由 rollout 反馈持续更新的任务上下文。

skill 是否有效，必须由训练任务和独立验证任务上的指标共同判断。对多 Agent，真需求不是模拟一个热闹组织，而是并行搜索多个假设并隔离上下文污染。主 Agent 必须承担调度与汇总责任，子 Agent 必须产出可持久化、可比较的结果。

对用户当前目标，真需求是构建一个能持续复用个人判断、真实案例和失败经验的工作流底座，使 deepweek、信息雷达和个人 IP 不再是彼此割裂的自动化脚本，而是共享文件化记忆、评估机制和可演化 skill 的 Agent 系统。

8. 硬核保留

以下框架是根据原文方法抽象，并非原文逐字给出的完整模板。

  • 明确目标、约束、权限和验收指标。
  • 读取当前状态及最相关的上下文条目，不加载全部历史。
  • 生成计划，并标出可并行的独立假设。
  • 执行动作或启动子 Agent，将输出写入文件。
  • 通过测试、证据链或量化指标验证结果。
  • 若失败，读取错误日志并定位原因，不直接重复同一动作。
  • 提炼一条可复用经验，以“标识符＋描述＋证据来源”增量写入行动手册。
  • 达标后提交产物；未达标则改进计划并进入下一轮。三、子 Agent 调度 checklist： □ 子任务之间是否真正独立？□ 每个任务是否有明确输入、输出文件和验收标准？□ 是否记录任务编号、运行状态、日志路径和产物路径？□ 主 Agent 能否检查、超时取消和失败重试？□ 输出是否持久化，而非只存在于聊天上下文？

一、Harness 目录框架： /agent-name/ skill.md：目标、约束、工具、操作步骤与停止条件 context/：带标识符的长期经验条目 state/：当前任务状态、检查点、待处理队列 rollouts/：每次执行的输入、动作、观察与结果 artifacts/：报告、代码、数据和内容成品 jobs/：子 Agent 或后台任务的状态与日志 evals/：测试集、评分规则、训练与验证指标 harness/：工作流、检索、过滤和调度代码 二、目标导向 loop：

□ 汇总时是否比较冲突、证据强弱和重复项？四、ACE 式上下文更新 prompt： “读取本轮成功与失败轨迹。仅提炼会改变未来决策的经验，每条输出为 {id, description, evidence, scope}。不得重写完整行动手册；不得把一次性任务事实升级为通用规则；与已有条目重复时执行合并，发生冲突时保留适用条件；

说明该条目来自成功经验还是失败修正。” 五、MCE 式双层优化： 基础层：固定当前 skill，在 rollout 反馈下优化搜索、选择、过滤和格式化方式，得到更有效的上下文函数。元层：保存每版 skill、上下文函数、训练指标和验证指标；编码 Agent 基于历史版本组合出新 skill；只在独立验证集提升时晋级，防止对历史任务过拟合。

六、Harness 变更验收 checklist： □ 新版本是否在真实任务或回归集上运行过？□ 是否同时比较成功率、成本、时延和人工介入次数？□ 是否减少无效上下文，而非仅增加更多规则？□ 失败是否留下可检索的轨迹和错误日志？□ 中断后能否从文件状态恢复？□ 是否保留旧版本并支持回滚？□ 改进来自通用机制，还是只对单个样例有效？

□ 只有达标候选才进入正式运行环境。
