智能成本趋近于零后，Agent 需要怎样的数据系统

Intelligence is Free, Now What? — Data Systems for, of, and by Agents

打开原文 ↗

这不是原文摘要，而是把文章先翻译成中文语义后，再拆成可复用的思考方式、方法论和行动线索。

1. 核心观点

作者用“For、Of、By Agents”把未来的数据系统分成三层。第一层是面向 Agent 的数据系统（Data Systems For Agents）：Agent 不像人或传统 BI 工具那样一次提交一条精心构造的 SQL，而会进行“Agent 式推测”，先理解模式和字段，再并行探索假设，逐步形成查询。

一个用户问题可能触发数千条 SQL，其中大量子查询重复。数据系统因此不能继续只是被动执行器，而应主动复用重叠计算、返回近似或流式结果、预估查询延迟，并用更高层的循环和批量原语帮助 Agent 搜索。

第二层是由 Agent 构成的数据系统（Data Systems Of Agents）：当数千个 Agent 执行长期任务时，需要独立于模型推理服务的运行底座，负责状态、结构化记忆、并发编辑、通信、共识、失败恢复和慢节点处理。Claude Code、Codex 一类 harness 只是早期形态；

文件、Bash 和 Markdown 仍然重要，但不足以支撑大规模协作。第三层是由 Agent 创建的数据系统（Data Systems By Agents）：随着 Agent 能按工作负载现场生成定制数据系统，工程瓶颈从“能不能生成”转向“如何验证生成系统符合意图并值得信任”。原文在截断处尚未展开验证方案，但已明确把可信验证视为核心挑战。

全文隐含的架构转向是：模型只是廉价智能供应层；真正决定 Agent 系统能力上限的，是 harness 和数据底座能否减少无效探索、沉淀纠错经验，并让大量 Agent 在共享状态上稳定收敛。

2. 关键论据

论据一：智能正在快速商品化。GPT-4 级能力在 2023 年初约为每百万 token 30 美元，如今已低于 1 美元，部分供应商低于

  • 1 美元；各类基准上的推理价格每年下降约 9 至 900 倍，中位数接近 50 倍。作者并不要求“诺奖级智能”已经出现，只要求现有智能足以完成大多数日常知识工作。论据二：更多 Agent 尝试确实能提高任务成功率，但会产生巨量重复计算。

在多 Agent text-to-SQL 实验中，只有约 10%至20%的子计划彼此不同，意味着80%至90%的子查询在重复工作。这种冗余对搜索成功有益，对底层数据系统却是浪费，因此应该保留探索多样性，同时复用公共计算。论据三：复杂数据任务天然是组合搜索问题。根因分析、流失人群探索等任务涉及大量连接、聚合和过滤条件组合。

让 Agent 显式枚举每条 SQL，会浪费推理能力；数据系统应提供批查询、近似要求、循环宏或面向分析目标的高层原语。论据四：把所有长期经验写进 Markdown，再通过关键词或向量相似度塞回上下文，迟早会失效。上下文有限，即使窗口持续扩大，也存在延迟和序列化成本；大型数据库、代码库和企业知识不可能全部放进提示词。

论据五：未经整理的 Agent 轨迹会传播错误。原始执行记录包含失败尝试和错误判断，如果直接召回，后续 Agent 可能重复犯错。有效记忆必须把轨迹提炼成具有适用范围的纠错知识。论据六：多 Agent 不只是多开几个模型实例，还会引入共享状态冲突、事务回滚、重复执行、Agent 失败、慢 Agent、共识形成及活锁等分布式系统问题。

3. 方法论

第一步，改变工作负载假设。不要把 Agent 当成更快的人类用户，而要承认它会高频、并行、异构地探索：读取模式、检查字段、构造局部计划、尝试查询、接收反馈，再修正下一步。第二步，把“有益冗余”和“无效重复”分开。多次独立尝试可以扩大假设空间、提高成功率，因此不应简单限制 Agent 数量；

底层应识别公共子计划，通过多查询优化、共享扫描、结果缓存等方式，只计算一次、供多个 Agent 复用。第三步，允许渐进式求解。探索阶段不一定需要完整精确结果，可以先返回近似答案、算子中间结果或流式样本，让 Agent 判断是否值得继续。系统还可在执行昂贵查询前反馈预估延迟，促使 Agent调整方案。第四步，提升交互抽象层级。

把“一次一条 SQL”升级为批查询加独立近似要求，或提供类似 DBT Jinja 宏的循环原语，让 Agent 描述搜索模式，而不是手工枚举指数级查询空间。第五步，让数据系统主动参与推理闭环。系统利用自己对数据分布、模式和性能的了解，主动推荐相关查询、准备物化视图或虚拟视图，并把这些信息作为上下文反馈给 Agent。

第六步，把记忆从文档堆升级为结构化、可过滤的纠错记录。每条记忆至少包含适用维度、匹配值和自然语言指令。例如数据 Agent 可按表、字段、操作类型过滤，再返回“日期计算使用财年”“产品名优先使用清洗字段”等纠正规则。第七步，把多 Agent harness 当作分布式执行系统设计：长期任务必须有持久状态、重试与恢复；

共享修改需要版本、写入隔离、幂等或恰好一次语义；并行候选事务大多需要回滚，只让最终正确结果提交；通信与共识机制必须避免 Agent 互相补偿导致活锁。第八步，用 Agent 反过来维护系统。

作者提出，具体应用的记忆模式类似数据库 schema，可以让 Agent 在运行中帮助定义和持续细化，进而从大量单 Agent、多 Agent 轨迹中挖掘规律，推动基于结构化记忆的递归改进。

4. 金句摘录

“virtually free intelligence”——“近乎免费的智能”。关键不在于智能是否达到天才水平，而在于完成大多数知识工作的能力正在迅速降价并可以被大规模调用。“Data Systems For, Of, and By Agents”——“面向 Agent、由 Agent 构成、由 Agent 创建的数据系统”。

这是全文最重要的三层分析框架，分别对应交互优化、运行底座和可信生成。“agentic speculation”——“Agent 式推测”。Agent 会并行试探大量假设，而不是像传统应用一样提交少量稳定查询；因此探索过程本身成为数据系统的主要工作负载。

“only 10-20% of the sub-plans are distinct”——“只有10%至20%的子计划是不同的”。它揭示了多 Agent 搜索的核心矛盾：冗余能提高成功率，却会把计算成本放大到难以接受。“files are all you need”——“文件就是你所需要的一切”。

作者先承认文件、Bash 和 Markdown 在当前 Agent harness 中的重要性，随后指出它们无法承担大规模、长期、多维检索和并发修改的全部职责。“raw agent traces with mistakes are not very useful”——“带有错误的原始 Agent 轨迹并没有多大用处”。

记忆不是保存得越多越好，未经提炼的失败轨迹会诱导未来 Agent 重复错误；真正应沉淀的是带适用范围的纠错知识。“step on each other’s toes”——“互相踩脚”。这形象概括了多 Agent 共享状态的主要风险：每个 Agent 都可能具备语义推理能力，但并发补偿和回滚仍可能让整体无法前进。“livelock”——“活锁”。

系统看似一直在行动，各 Agent 也不断修正彼此，但没有任何有效进展；这是设计多 Agent loop 时必须显式监控的失败状态。

5. 我的行动

一、Deepweek 个人助手：保留 Markdown 作为人可读出口，但新增结构化事项与记忆层。事项至少包含长期目标、本周一事、模块、截止时间、优先级、依赖、状态和排序理由；经验记忆至少包含场景、适用模块、触发条件、纠错指令、证据和更新时间。这样“今日上分／别掉血”的排序不只依赖语义召回，而能按目标、时间、事项类型精确过滤。

每次调整计划时记录“建议、用户修正、最终规则”，不要把整段对话直接当记忆。二、AI Signal Radar：把抓取、三个月过滤、去重、影响力评分、深读和发布拆成有持久状态的 Agent stages。多个来源 Agent 可以并行探索，但应共享 URL 规范化、主题聚类、实体识别和历史入库结果，避免每个 Agent 重复抓取和判断。

对候选内容先运行低成本近似筛选，再对高影响候选执行完整原文抓取与深读。失败任务必须支持断点续跑，正式入库只能由最终提交节点执行，防止重复发布。三、930 前工作流 Agent 化：不要把目标理解成“所有步骤都调用大模型”，而要建立统一 harness。

最小能力包括任务状态机、Agent 角色与权限、结构化输入输出、共享记忆、幂等键、重试策略、超时、回滚、人工审批点、成本与延迟记录。优先 Agent 化规则明确、频率高、可验证的流程，再处理开放性决策。

四、个人 IP 创建：建立“选题探索 Agent—证据整理 Agent—观点提炼 Agent—平台改写 Agent—事实与重复检查 Agent—人工发布”的 loop。多个创作 Agent可提出不同角度，但不要各自重复读取全部素材；先生成统一证据包和个人经验包供它们共享。最终文章只提交一个版本，其余候选保留为分支，不直接污染正式知识库。

五、马上补一张 Agent 运行表：为每次任务记录 request_id、agent_id、parent_id、阶段、输入引用、输出引用、开始与结束时间、token 成本、工具调用、状态、失败类型、重试次数和提交版本。先获得真实轨迹，才能识别重复子计划、慢 Agent、无效 loop 和可沉淀的纠错记忆。

六、建立每周记忆提炼任务：从失败与人工修改中抽取纠错规则，经验证后写入结构化记忆；原始轨迹只作审计证据，不直接进入默认上下文。

6. 第一性原理

第一，廉价不等于免费。单次推理成本下降后，系统会自然增加 Agent 数量和尝试次数，总成本可能被数千次查询、重复上下文和无效循环重新放大。因此要优化的不是单次调用，而是完成一个可靠结果所需的总计算量与总延迟。

  • 第二，探索冗余本身不是缺陷。多个 Agent 独立尝试能够覆盖更大的假设空间，提升任务成功率。真正的问题是相似探索在底层重复读取、扫描和计算。正确策略是保留认知层的多样性，同时合并执行层的公共工作。
  • 第三，Agent 的上下文不是数据库。上下文适合承载当前决策所需的少量信息，不适合充当所有历史、代码、业务数据和协作状态的永久容器。长期知识必须可查询，运行状态必须可事务化，最终只把与当前任务匹配的信息送入上下文。
  • 第四，记忆的价值取决于可用性，而不是体积。有效记忆需要回答三个问题：它适用于什么对象、在什么条件下触发、应该纠正什么行为。原始轨迹只说明曾经发生过什么，结构化纠错规则才能指导未来行动。
  • 第五，多 Agent 协作首先是状态协调问题，其次才是对话问题。Agent 能用自然语言沟通，并不自动带来一致性；只要它们并发修改同一对象，就必须处理版本、冲突、重复执行、回滚和最终提交。
  • 第六，loop 必须有单调进展指标。若每次循环只是重新生成、互相否定和反复补偿，更多智能只会加速活锁。每轮应减少未解决约束、提升证据覆盖、降低候选数量，或推进一个明确状态。
  • 第七，生成能力越强，验证责任越重。Agent 能一次生成完整数据系统，不代表系统满足隐含业务语义。未来 AI coding 的核心竞争力将从代码产量转向规范表达、自动验证、可追踪证据和安全提交。

7. 真需求

表面需求是让 Agent 自动查数据、收集信息、安排任务或生成内容；底层真需求是，在不把人工监督成本同步放大的前提下，持续得到可信、可解释、可恢复的结果。对数据分析而言，真需求不是自动生成更多 SQL，而是让系统高效覆盖假设空间，并尽早判断哪些方向值得继续。近似结果、延迟反馈、共享子计划和高层分析原语，都是为了降低“找到有效答案”的总成本。

对长期助手而言，真需求不是记住更多聊天，而是在正确场景召回正确规则。Deepweek 需要的是按目标、日期、事项类型和用户偏好匹配的结构化记忆；AI Signal Radar 需要的是按来源、主题、时间窗口、影响维度和重复关系匹配的筛选记忆。

对多 Agent 而言，真需求不是让角色彼此聊天得更像团队，而是让不同目标下的并行工作最终收敛：哪些状态可以共享，谁有提交权，冲突如何处理，失败如何恢复，何时停止探索，都必须被 harness 明确定义。对 AI coding 而言，真需求不是让 Agent 更快写出一套数据系统，而是把预期行为变成可执行规范，并证明生成结果满足这些规范。

没有验证闭环，“By Agents”只会把开发瓶颈转移为验收瓶颈。因此，工作流 Agent 化的正确验收指标应是：端到端成功率是否提高、人工修正是否减少、失败是否能恢复、重复工作是否下降、关键结论是否有证据、最终写入是否幂等，而不是一共部署了多少 Agent。

8. 硬核保留

以下模板是根据原文方法抽象，并非作者逐字给出的现成模板。 一、Agent 工作负载评审清单：

  • 一个用户请求最多会派生多少 Agent、子任务和数据查询？
  • 哪些子计划可能重叠，能否用结果缓存、共享扫描或公共中间结果复用？
  • 哪些阶段只需样本、近似值或流式中间结果，哪些阶段必须精确？
  • 能否批量提交候选查询，并为每个查询声明精度、成本和延迟要求？
  • 是否存在可封装为循环宏或高层原语的组合搜索？
  • 数据系统能否主动返回相关结果、推荐视图、数据分布和延迟预估？
  • 为整个请求生成唯一 request_id，每个候选分支生成 branch_id。
  • Agent 只在分支状态上修改，不直接写正式结果。
  • 工具调用携带幂等键，重试不得制造重复副作用。
  • 对公共输入和中间结果做内容寻址，重复子计划直接复用。
  • 每个分支产出结果、证据、约束满足情况和未解决问题。
  • 仲裁节点比较候选并形成唯一 commit proposal。
  • 验证节点执行规则、测试、事实和权限检查。
  • 只有验证通过的提案可原子提交；其他分支回滚或归档。
  • 监控活锁：若连续多轮未减少错误、未增加证据、未改变候选排名，则停止并升级人工处理。四、可复用的 Agent 规划提示词： “你正在处理任务：{task}。不要立即枚举全部操作。先输出：①需要探索的假设空间；②可并行的候选分支；③各分支可能共享的子计划或数据读取；④哪些步骤可用近似、抽样或流式结果提前判断；⑤必须精确验证的最终条件；⑥每轮进展指标；
